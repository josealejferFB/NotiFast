# Especificación de Diseño: Motor de Notificaciones Proactivas con WorkManager (Sprint 3.1)

## 📌 1. Resumen Ejecutivo
Esta especificación define la arquitectura técnica, modelos de datos, Use Cases y configuración de background workers para el **Sprint 3.1** de NotiFast v3.0 (Fase 3).

El objetivo es dotar a NotiFast de un motor proactivo de notificaciones locales ejecutado mediante **Android WorkManager** y **Hilt**, que alerte al estudiante oportunamente sobre:
1. **Evaluaciones Próximas:** Recordatorios $N$ días antes (configurado en `evalAlertDays`, ej. 1, 2, 3 o 7 días antes a las 09:00 AM) y el mismo día del examen/entrega.
2. **Clases Inminentes:** Alertas $M$ minutos antes (configurado en `classAlertMinutes`, ej. 10, 15, 30 min) con salón, profesor y acceso al aula virtual.
3. **Resumen Diario Matutino:** Notificación matutina periódica (07:00 AM) con las clases del día y entregas en las próximas 48 horas.

Todo el procesamiento es **100% local y offline**, protegiendo la privacidad del estudiante y garantizando 0 consumo de cuotas en Firebase Spark Free Tier.

---

## 🎯 2. Requisitos y Restricciones Globales

1. **Infraestructura de Fondo Resiliente:**
   - Uso de `androidx.work:work-runtime-ktx` con `@HiltWorker` y `HiltWorkerFactory`.
   - `ExistingWorkPolicy.REPLACE` con tags deterministas basados en ID (`eval_{id}`, `class_{id}`, `daily_summary`) para cancelación y actualización en $O(1)$.
   - `BootCompletedReceiver` para reprogramación automática tras reinicio del dispositivo.
2. **Canales de Notificación NotiFast (Material 3 & Tactile Studio):**
   - Canal 1: `notifast_evaluations` — *Evaluaciones y Exámenes* (Alta prioridad / Importancia MAX con sonido y vibración).
   - Canal 2: `notifast_classes` — *Horarios y Clases* (Prioridad Default / HIGH con vibración táctil).
   - Canal 3: `notifast_daily_summary` — *Resumen Diario* (Prioridad Default con estilo InboxStyle o BigTextStyle).
3. **Manejo de Permisos Android 13+ (`POST_NOTIFICATIONS`):**
   - Diálogo explicativo previo (`NotiFastDialog`) antes de lanzar el request del sistema si las alertas están activas o al crear la primera evaluación/clase.
4. **Higiene de Código & Clean Architecture:**
   - Composables y clases $\le 200$ líneas de código.
   - Cero strings quemados (100% en `strings.xml`).
   - Cero lógica de negocio en workers/composables; toda la lógica de cálculo temporal reside en `domain/usecase/` y `domain/util/`.
   - Todas las operaciones de fondo retornan `Result<T>` o `ListenableWorker.Result`.

## 🏗️ 3. Arquitectura del Sistema

```
app/src/main/java/com/notifast/app/
├── data/
│   ├── notification/
│   │   ├── NotificationChannelsManager.kt      # Creación de canales en Android O+
│   │   ├── NotificationSender.kt               # Construcción y envío de notificaciones NotificationCompat
│   │   └── BootCompletedReceiver.kt            # BroadcastReceiver tras reinicio del sistema
│   └── worker/
│       ├── EvaluationReminderWorker.kt         # Worker OneTimeWork para alertas de exámenes
│       ├── ClassScheduleWorker.kt              # Worker OneTimeWork para alertas de clases
│       └── DailySummaryWorker.kt               # Worker PeriodicWork (07:00 AM) para resumen matutino
│
├── domain/
│   └── usecase/
│       ├── ScheduleEvaluationAlertUseCase.kt   # Cálculo de delay temporal y enqueue en WorkManager
│       ├── ScheduleClassAlertUseCase.kt        # Cálculo de próxima ocurrencia y enqueue
│       ├── CancelAlertUseCase.kt               # Cancelación por tag determinista
│       └── RescheduleAllAlertsUseCase.kt       # Sincronización masiva de todas las alertas activas
│
└── presentation/
    └── feature/settings/
        └── (Hooks reactivos conectados a UserPrefsRepository existentes)
```

## ⚙️ 4. Especificación Técnica de Componentes

### 4.1. Configuración de WorkManager con Hilt
- `libs.versions.toml`:
  - `workRuntime = "2.10.0"`
  - `hiltWork = "1.2.0"`
  - `androidx-work-runtime-ktx = { group = "androidx.work", name = "work-runtime-ktx", version.ref = "workRuntime" }`
  - `androidx-hilt-work = { group = "androidx.hilt", name = "hilt-work", version.ref = "hiltWork" }`
  - `androidx-hilt-compiler = { group = "androidx.hilt", name = "hilt-compiler", version.ref = "hiltWork" }`
- `NotiFastApplication.kt`:
  - Implementa `Configuration.Provider`.
  - Inyecta `@Inject lateinit var workerFactory: HiltWorkerFactory`.
  - Override `val workManagerConfiguration: Configuration get() = Configuration.Builder().setWorkerFactory(workerFactory).build()`.

### 4.2. `NotificationChannelsManager.kt`
- Inicializa canales en `NotificationManagerCompat`:
  - `CHANNEL_EVALUATIONS = "notifast_evaluations"` (Importancia: `HIGH`, vibración habilitada).
  - `CHANNEL_CLASSES = "notifast_classes"` (Importancia: `HIGH`, vibración habilitada).
  - `CHANNEL_DAILY_SUMMARY = "notifast_daily_summary"` (Importancia: `DEFAULT`).
- Se invoca en `NotiFastApplication.onCreate()`.

### 4.3. `NotificationSender.kt`
- Funciones de conveniencia para construir `NotificationCompat.Builder`:
  - `sendEvaluationNotification(id: String, subjectName: String, title: String, dateText: String, weight: Double)`
  - `sendClassNotification(id: String, subjectName: String, classroom: String, timeText: String, meetUrl: String?)`
  - `sendDailySummaryNotification(classesCount: Int, evalsCount: Int, summaryBody: String)`
- Deep Link: `PendingIntent` hacia `MainActivity` con flags `FLAG_IMMUTABLE | FLAG_UPDATE_CURRENT`.

### 4.4. Workers Hilt (`@HiltWorker`)

1. **`EvaluationReminderWorker` (`@AssistedInject` constructor):**
   - Recibe `evaluationId`, `subjectName`, `evalTitle`, `evalDate`.
   - Consulta `UserPrefsRepository` (`evalAlertsEnabledFlow.first()`). Si está deshabilitado, termina con `Result.success()`.
   - Consulta `EvaluationRepository.getEvaluation(userId, evaluationId).first()`. Si ya no existe o su nota ya fue asignada (`grade != null`), no notifica.
   - Si sigue activa, emite la notificación mediante `NotificationSender`.

2. **`ClassScheduleWorker` (`@AssistedInject` constructor):**
   - Recibe `scheduleId`, `subjectName`, `dayOfWeek`, `startTime`, `classroom`, `meetUrl`.
   - Consulta `UserPrefsRepository` (`classAlertsEnabledFlow.first()`).
   - Verifica existencia en `ScheduleRepository`.
   - Emite la notificación de clase inminente.
   - Encola automáticamente la ocurrencia de la siguiente semana (7 días después) para mantener el ciclo activo.

3. **`DailySummaryWorker` (`@AssistedInject` constructor):**
   - Consulta `UserPrefsRepository` (`dailySummaryEnabledFlow.first()`). Si es falso, termina.
   - Obtiene horarios del día actual y evaluaciones dentro de las próximas 48 horas.
   - Construye texto condensado (ej. *"Hoy: 2 clases (Cálculo a las 08:00 AM) • 1 entrega pendiente mañana"*).
   - Emite la notificación.

### 4.5. Casos de Uso en `domain/usecase/`

1. **`ScheduleEvaluationAlertUseCase`:**
   - Parámetros: `evaluation: Evaluation`, `daysInAdvance: Int? = null`.
   - Lógica:
     - Parsea `evaluation.date` (`yyyy-MM-dd`).
     - Calcula `targetTime = date - (daysInAdvance ?: userPrefs.evalAlertDays) días a las 09:00 AM`.
     - Si `targetTime <= now`, no encola o encola para el mismo día a las 08:00 AM si aún no ha pasado la hora.
     - `val delay = targetTime - now`.
     - Tag: `"eval_${evaluation.id}"`.
     - `WorkManager.enqueueUniqueWork("eval_${evaluation.id}", ExistingWorkPolicy.REPLACE, workRequest)`.

2. **`ScheduleClassAlertUseCase`:**
   - Parámetros: `schedule: Schedule`, `minutesInAdvance: Int? = null`.
   - Lógica:
     - Calcula la próxima fecha/hora correspondiente a `schedule.dayOfWeek` y `schedule.startTime` (`HH:mm`).
     - Resta `minutesInAdvance ?: userPrefs.classAlertMinutes`.
     - `val delay = nextOccurrence - now`.
     - Tag: `"class_${schedule.id}"`.
     - `WorkManager.enqueueUniqueWork("class_${schedule.id}", ExistingWorkPolicy.REPLACE, workRequest)`.

3. **`CancelAlertUseCase`:**
   - Parámetros: `tag: String` (ej. `"eval_${id}"` o `"class_${id}"`).
   - Lógica: `WorkManager.cancelUniqueWork(tag)`.

4. **`RescheduleAllAlertsUseCase`:**
   - Obtiene todas las evaluaciones activas y horarios del usuario autenticado.
   - Reprograma todas las alertas con la configuración vigente de `UserPrefsRepository`.

### 4.6. `BootCompletedReceiver.kt`
- Anotado con `@AndroidEntryPoint`.
- Filtra acción `Intent.ACTION_BOOT_COMPLETED`.
- Ejecuta `RescheduleAllAlertsUseCase` en una coroutine con `CoroutineScope(Dispatchers.IO)`.

## 🧪 5. Estrategia de Testing (TDD)

Se construyen pruebas unitarias aisladas en `app/src/test/java/com/notifast/app/domain/usecase/`:
1. `ScheduleEvaluationAlertUseCaseTest`:
   - Programación con fecha futura (ej. 3 días después) ➔ Calcula delay correcto.
   - Programación con fecha pasada ➔ No encola o maneja caso borde sin crashear.
   - Verificación de Tag determinista `"eval_{id}"`.
2. `ScheduleClassAlertUseCaseTest`:
   - Clase hoy en 2 horas con alerta de 15 min ➔ Delay de 1h 45m.
   - Clase que ya pasó hoy ➔ Programa para el mismo día de la próxima semana.
   - Verificación de Tag determinista `"class_{id}"`.
3. `CancelAlertUseCaseTest`:
   - Verificación de llamada a `WorkManager.cancelUniqueWork`.

## 🔒 6. Seguridad, Permisos y Consumo de Recursos
- **Permisos en `AndroidManifest.xml`:**
  - `<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />`
  - `<uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED" />`
- **Consumo de Batería:** Trabajo diferido mediante WorkManager respetando los estados Doze de Android.
- **Cuotas Free Tier:** $0$ costo en Firebase y cero consumo de ancho de banda.
